## What This Is

Metap is a metadata-driven platform. The core idea: entity behavior (fields, list views, validation, workflow) is declared once as metadata, and CRUD/list/workflow behavior is generated from it — but each concern (metadata, permission, query planning, workflow, outbox) is an explicit service with a fixed boundary, not a grab-bag helper.

- **`metap-auth`** (`docs/roadmap/25-tenant-auth-pluggable.md`) — tenant-selectable auth *providers* (`AuthProviderKind`: `Local`/`Basic`/`Oidc`) — distinct from `metap-http::auth`'s per-request session verification, this is how a tenant's own users actually log in. A tenant can enable more than one provider at once (`tenant_auth_configs` allows N rows per tenant, not one exclusive strategy); `Local`/`Basic`/`Oidc` take genuinely different inputs (password vs an OIDC redirect code), so this is a discriminant config picks from, not a `dyn` trait every provider must uniformly implement. Bearer (JWT) itself is not a provider here — it's the session mechanism every successful login ends in (`metap_peripherals::mint_jwt`), verified per-request by `metap-http::auth::AuthContext`, unchanged by this crate. No HTTP, no business-entity knowledge — a plain library, same shape as `metap-permission`. Re-exported by the facade as `metap::tenant_auth`.
- **`metap-jwks`** / **`metap-jwks-http`** (Phase 49) — a multi-service Ed25519 JWKS trust root: any service can verify a token signed by any other service's private key without sharing secrets, a step up from the single-static-keypair-per-app model (`metap-http::auth::AuthContext`'s `TokenVerifier::Static`) every binary still defaults to. 3-step rotation (add new key as non-primary → flip primary → retire old key after its tokens expire), `JwksClient` caches the public-key set with a TTL. Opt-in — no binary this repo's crates are actually run by (`../metap-demo-crm`/`../metap-demo-jira`) has switched its own `AuthContext`/`GrpcRecordService::AuthConfig` over to `TokenVerifier::Jwks` yet; each still verifies with its own static keypair. No HTTP surface of its own beyond `metap-jwks-http`'s `/.well-known/jwks.json`-shaped endpoint.
- **`metap-grpc`** (Phase 49) — generic, metadata-driven CRUD-over-gRPC (`RecordService`, `proto/metap_crud.proto`, codegen via `protoc-bin-vendored`+`tonic-prost-build`, no system `protoc` needed): `list`/`get`/`create`/`update`/`transition`/`delete` for *any* entity a `MetadataRegistry` knows, mirroring how `/api/:entity*` (REST) is already entity-generic. `GrpcRecordService` (server) calls straight into `metap_crud::CrudService`, so permission/validation/workflow behavior can't drift from REST. `serve()` runs on its own port via `tokio::spawn` (needs HTTP/2-only serving, can't share axum's REST listener) — opt-in per binary via `GRPC_ENABLED`/`GRPC_PORT` (`../metap-demo-jira`, `../metap-demo-crm` since Phase 50). `client` module's `GrpcBackend` (Phase 50) is the *client* side — implements `metap_crud::RecordBackend` (below) by calling a remote `RecordService`, authenticating with the caller's own forwarded bearer token when present (`RequestContext::forwarded_bearer_token`, real-identity propagation added 2026-09-02), else a per-upstream `ServiceTokenSource` — a real user this process logs into that upstream's own `POST /auth/login` with, refreshed automatically in the background well before the token expires (replaced a static, hand-minted-once service JWT after that JWT's 1h TTL expired in a running deployment and crashed a caller at boot). `ServiceTokenSource` itself lives in `metap-runtime` (`client.rs` re-exports it) since `cron-scheduler` also uses it directly over REST — this is what `crates/graphql-gateway` connects with. `google.protobuf.Struct` carries record data (JSON-shaped, no per-entity proto message) — `convert.rs`'s `struct_to_json`/`json_to_struct` do the (mostly lossless — numbers reconstruct as integers where exact) round trip.
- **`metap-graphql`** / **`metap-graphql-http`** (Phase 49) — generic, metadata-driven GraphQL: one schema built dynamically at runtime from a `MetadataRegistry` via `async-graphql`'s `dynamic` module (entities aren't known at compile time, same reason `metap-metadata::openapi.rs` can't `#[derive(JsonSchema)]`). Every entity gets `Query.{camel}(id)`/`Query.{camel}List(...)`/`Mutation.create{Type}`/`update{Type}`/`delete{Type}`/`transition{Type}` (workflow entities only). DataLoader batching (`RecordLoader`, keyed `(entity, id)`), complexity/depth limits (`SchemaLimits`), and field-level permission masking (free — every resolver reads an already-`filter_readable_fields`-masked `RecordDto`, same masking REST already runs) are all handled without entity-specific code. **`build_schema`/`with_request_data`/`RecordLoader` take `Arc<dyn RecordBackend>`, not `Arc<CrudService>`** (Phase 50) — the seam that lets the exact same resolver code serve either an in-process `CrudService` (`../metap-demo-jira`/`../metap-demo-crm`, each mounting `metap-graphql-http::router()` for their own entities only) or a remote `CompositeBackend` routing by entity name to several different microservices' `GrpcBackend`s (`crates/graphql-gateway`, the real cross-service BFF — see that crate's own bullet below for the distinction from a single service's own GraphQL mount). `metap-graphql-http::playground_router` (GraphiQL, non-production only) is generic over `Router<S>` for this same reason — the gateway has no `AppState` to serve it through.
- **`metap-peripherals`** — index reconciler, metadata drift check, role assignment (grant/revoke/list).
- **`metap-storage`** (Phase 22) — `ObjectStore` trait (`put`/`get`/`delete`/`exists`, plain key/bytes, no S3 concepts leak into the trait itself) + `S3ObjectStore`, its only impl, built on `aws-sdk-s3` against a configurable `endpoint_url` — works unmodified against SeaweedFS (`docker-compose.yml`'s opt-in `seaweedfs` service, this project's current pick after MinIO's OSS edition was archived April 2026) or any other S3-API-compatible server by changing config alone, same swappable-backend shape as `SecretStore`/`EventBus`. Security-first by construction, not caller discipline: every method takes `tenant_id: Uuid` as its first parameter and `S3ObjectStore` builds the real key (`{tenant_id}/{key}`) internally — no call site can construct a request that touches another tenant's objects — and `validate_key` rejects a traversal-shaped (`..`/leading `/`) or malformed key before it ever reaches the backend, same discipline as `Router::validate_schema_name`. `S3ObjectStoreConfig`'s credentials are `secrecy::SecretString`, matching `metap-control::DbCreds`. Wired end to end since `metap-attachments` shipped (below) — `AppState.object_store` backs `crates/metap-http/src/routes/attachments.rs`'s upload/list/download/delete; an app with `metap-storage` unconfigured gets a plain `503` from those routes instead. No HTTP, no business-entity knowledge — a plain library, same shape as `metap-permission`.
- **`metap-attachments`** (Phase 27, `docs/roadmap/27-attachments-platform.md`) — file attachment metadata, `metap-storage::ObjectStore`'s first real consumer. Deliberately not a metadata-driven `EntityDefinition`: `record_id` can point at a row in *any* entity's table, which rules out a typed `Reference` foreign key — same category as `policies`/`cron_jobs`, a plain platform table. Every function takes a `table_name: &str` rather than hardcoding one — a caller passes the shared default table for most entities, or a dedicated table (`ensure_dedicated_table`) for one expecting heavy attachment volume. Known tradeoff, not a bug: nothing here blocks deleting the record an attachment points at (no cross-table DB-level FK possible, and no `metap-*` core crate is allowed to know this concept exists) — a dangling metadata reference, not data loss (the blob itself is untouched). `crates/metap-http/src/routes/attachments.rs` is the HTTP surface; its own permission check is record-level (ABAC), not just entity-level, via `metap_crud::CrudService::check_record_permission` (2026-09-02, see that method's doc comment for the bug this closed). No HTTP of its own, no business-entity knowledge — a plain library, same shape as `metap-cron`.
- **`metap-cache`** (Phase 23) — `Cache` trait (`get`/`set`/`invalidate`, tenant-scoped like `ObjectStore`, one fixed TTL per instance set at construction rather than a per-call `ttl`) + 2 impls: `MokaCache` (in-process, same `moka` library `RegistryCache`/`ContextAttributesCache` already use) and `RedisCache` (distributed, over any RESP-protocol server — Redis/DragonflyDB/Valkey/KeyDB are wire-compatible, so swapping the actual backend is a connection-string change, not a code change; DragonflyDB is what `docker-compose.yml`'s opt-in `dragonfly` service runs for local dev). First real consumer: `PermissionService::with_cache` (alongside the existing `PermissionService::new`, which stays fully uncached — every existing call site is unaffected) caches `load_snapshot`'s policy-row lookups (`policies:{entity}`, tenant-scoped), invalidating on `create_policy`/`delete_policy` rather than only waiting out the TTL. Opt-in via `POLICY_CACHE_REDIS_URL`/`POLICY_CACHE_TTL_SECONDS` (`metap-infra::AppConfig`) in `../metap-demo-crm`/`../metap-demo-jira`'s boot sequences. Role/`user_roles` data is never cached here or anywhere — see `metap-http`'s bullet below and `crates/metap-http/src/auth.rs`'s doc comment; only policy *rules* (admin-edited config) go through this cache, never role *assignment*. No HTTP, no business-entity knowledge — a plain library, same shape as `metap-permission`.
- **`metap-cron`** — `CronJob`/`CronJobRun` storage (`cron_jobs`/`cron_job_runs` tables — platform/ops config, not an `EntityDefinition`, same category as `policies`/`user_roles`), cron-expression + IANA-timezone occurrence math (`next_run_at`), and `claim_due_jobs` (the `FOR UPDATE SKIP LOCKED` claim `cron-scheduler`'s ticker calls). Also owns the metadata-driven workflow-automation layer built on top (`docs/features/02-workflow-engine.md`): `TargetType::Steps` (a sequential activity chain, `workflow_runs` table tracking progress) and, since Increment 3 (2026-08-28), `TargetType::WaitEvent` — a step valid only inside a `Steps` chain that durably pauses the chain (`workflow_runs`/`cron_job_runs` both `"waiting"`) until a matching domain event arrives (`pause_workflow_run`/`dispatch_on_wait_event_transition_matches`/`dispatch_on_wait_event_record_matches`; no timeout — a chain with no matching event waits indefinitely, a deliberate scope choice). No HTTP, no process loop — a plain library, same shape as `metap-permission`.
- **`metap-dashboards`** (`docs/roadmap/32-jira-jql-search-charts.md`'s "còn lại") — customizable dashboard layouts, a plain ops-config table (`dashboard_configs`), same shape as `metap-cron`/`policies`. Two levels, resolved by `get_effective_dashboard`: a **tenant default** (`owner_user_id IS NULL`, one per tenant, admin-write-only — that check belongs at the HTTP layer, this crate has no concept of roles) and a **personal override** (`owner_user_id = <user>`, any authenticated user writes only their own); a user with no personal layout falls back to the tenant default, a tenant with neither has nothing here at all (the caller supplies its own hardcoded starter widget set). No HTTP of its own, no business-entity knowledge — a plain library.
- **`outbox-publisher`** (binary + lib, package `metap-outbox-publisher`, lib name `outbox_publisher`) — the outbox drain/publish worker loop: polls `outbox_events` for unpublished rows and publishes each to `EventBus`. Runs as its own process by default (`cargo run --manifest-path crates/outbox-publisher/Cargo.toml`, against `config.outbox_database_url()`), or inline inside a host process via that process's own opt-in flag (see `../metap-demo-jira`'s `OUTBOX_WORKER_INLINE=true`) — both call the same `outbox_publisher::run(pool, bus, poll_ms, batch_size, shutdown)`, so the two deployment shapes can't drift apart, same pattern `notification-worker` established first. **The `pool` passed to `run()` must be wherever the tenant's own outbox rows actually live** — for a `DedicatedDb` tenant that's its own dedicated pool (`Router::pool_for`), never the platform's shared one; found live (2026-08-24) that `../metap-demo-jira`'s tenant had outbox rows sitting permanently unpublished because nothing was draining its dedicated database specifically. Ops tooling built on the library above, not itself entity-aware.
- **`notification-worker`** (binary + lib, package `metap-notification-worker`) — the first real consumer of `EventBus::subscribe`: binds a durable queue to `#.workflow.transitioned` and logs every entity's workflow transition (stdout only — no email/SMS/webhook integration exists yet). Runs as its own process by default (`cargo run --manifest-path crates/notification-worker/Cargo.toml`, mirroring `outbox-publisher`), or inline inside a downstream binary (`../metap-demo-crm`) via `NOTIFICATION_WORKER_INLINE=true` — both call the same `notification_worker::run`, so the two deployment shapes can't drift apart. Entity-agnostic like the other ops binaries.
- **`cron-scheduler`** (binary + lib, package `metap-cron-scheduler`) — the dispatch loop for `metap-cron`'s job definitions (`docs/roadmap.md` Phase 13): a ticker (polls `cron_jobs`) and an executor (runs a job) in one process. Each job's `dispatchMode` picks the path: `"outbox"` (default) — the ticker writes a `cron.job.due` outbox event per due job (reusing `outbox-publisher` to actually get it onto RabbitMQ, never publishing directly) and the executor subscribes to that routing key; `"direct"` — the ticker calls the executor's dispatch function in-process instead, skipping the outbox/RabbitMQ hop entirely (lower latency, but genuinely fire-and-forget — see `metap_cron::DispatchMode`'s doc comment). `workflow_transition`/`bulk_query_action` targets call back into a downstream binary's own `/api/:entity/...` HTTP surface (e.g. `../metap-demo-crm`) with a `metap_runtime::service_token::ServiceTokenSource` (`CRON_LOGIN_URL`/`CRON_SERVICE_EMAIL`/`CRON_SERVICE_PASSWORD` — a real user this process logs into that target's own `POST /auth/login` with and keeps fresh in the background, replacing a static, hand-minted-once `CRON_SERVICE_JWT` 2026-09-02) rather than linking `metap-crud`/`metap-metadata` directly — keeps this binary entity-agnostic, and gets permission/validation/audit for free. A missing/failing login degrades to an empty token (those two job types fail per-job, logged) rather than refusing to boot, since this process also runs job types (`webhook`, `email`) that don't need this credential at all. `webhook` targets call an arbitrary external URL. Run via `cargo run --manifest-path crates/cron-scheduler/Cargo.toml`.
- **`db-migrate`** (binary) — applies `crates/migrations/*.sql` via `sqlx::migrate!` to a fresh database. Replaces Drizzle's `db:generate`/`db:migrate`; there is no schema-diff tool anymore — new migrations are written by hand as new numbered `.sql` files in `crates/migrations/`.
- **`dev-tools`** (binary) — `gen-keys`/`mint-token`/`seed-admin`/`create-user`/`provision-tenant`/`bootstrap-platform-admin`/`enqueue-reconcile`/`vault-put-dsn`/`aws-secrets-put-dsn`/`gcp-secrets-put-dsn` subcommands, replacing the old `packages/core/scripts/*.mjs`. `enqueue-reconcile <tenantId> <entityName> <desiredVersion>` resolves the write through `Router::pool_for(tenantId)` (2026-08-28 — previously always wrote to the shared `DATABASE_URL` pool, which missed a `DedicatedDb` tenant's own copy of the queue) and calls `metap_reconciler::orchestrator::enqueue_deployment` — the manual trigger for `reconciler-orchestrator`'s ticker (now in `../metap-lowcode`) to pick up on its next poll (see `metap-reconciler`'s bullet above). `{vault,aws-secrets,gcp-secrets}-put-dsn <dsnSecretRef> <dsn>` write a `DedicatedDb` tenant's DSN into each of the 3 non-default `SecretStore` backends (`metap-control`'s bullet above). `mint-token` and `create-user` both call `metap_peripherals::mint_jwt`/`create_user` — the same functions `POST /auth/login` and `POST /admin/users` use — so a CLI-minted token or CLI-seeded user can't diverge from what a real login/admin-provisioned one looks like. `provision-tenant` calls the same `metap_control::provision_schema_tenant`/`provision_dedicated_db_tenant` `POST /platform/tenants` does (see `metap-control`'s bullet above), and for `dedicated_db` also runs `crates/migrations/*.sql` against the tenant's own database via the same `sqlx::migrate!` macro `db-migrate` uses. `bootstrap-platform-admin` is the only way to create the first platform-superadmin (no HTTP equivalent, same con-gà-quả-trứng reasoning as `seed-admin`) — grants the `"platform_admin"` role in `metap_control::PLATFORM_TENANT_ID`.
- **`graphql-gateway`** (binary + lib, package `metap-graphql-gateway`, Phase 50) — the real BFF: aggregates GraphQL across several **separately-deployed** microservices (`../metap-demo-jira` + `../metap-demo-crm` in the sibling-repo demo setup) into one schema, distinct from either binary's own `metap-graphql-http::router()` mount (which only ever serves that one service's own entities). Owns no entity, no Postgres, no `CrudService`. Boot: reads `UPSTREAM_<N>_{NAME,GRPC_ADDR,METADATA_URL,LOGIN_URL,SERVICE_EMAIL,SERVICE_PASSWORD}` env vars (N = 1, 2, ... until `_NAME` is missing), logs into each upstream's own `POST /auth/login`, `GET`s its `GET /metadata/entities` (bearer the token just obtained) to discover its schema, registers every entity into one shared `MetadataRegistry` (fails fast on a cross-upstream name collision — `MetadataRegistry::register`'s own duplicate check), connects one `metap_grpc::GrpcBackend` per upstream, and routes each entity to the right one via `metap_graphql::CompositeBackend`. Serves its own minimal `axum` app (`/health`, `/graphql`, `/graphql/playground` non-production) — not `metap_http::build_router`/`AppState`, which assume a Postgres pool this binary never has. **Auth at `/graphql` itself is decode-only** — a caller needs a token valid against this gateway's own keypair to reach it at all — **but identity propagates onward when the caller and an upstream share a keypair**: the caller's own token is forwarded verbatim (`RequestContext::forwarded_bearer_token`, set in `server.rs::authenticate`) and enforces that real caller's own permissions at the upstream, falling back to `ServiceTokenSource`'s login-based service-account token otherwise (see `metap-grpc`'s bullet above). Run via `pnpm gateway:rs`; see `crates/graphql-gateway/README.md` for a full local walkthrough against `../metap-demo-crm`/`../metap-demo-jira`.

## Architecture

Request flow is strictly layered, enforced by convention rather than tooling — do not shortcut it:

```
axum routes (crates/metap-http/src/routes/*)
  -> application service (crates/metap-crud/src/crud_service.rs)
    -> platform core (metap-metadata / metap-permission / metap-query / metap-workflow)
      -> Postgres (sqlx::PgPool, injected directly — no repository abstraction; see
         docs/architectures/09-adr.md for why)
      -> outbox (metap-infra::outbox::enqueue) -> RabbitMQ (metap-infra::EventBus)
```

There's no single DI container the way `packages/core/src/core/container.ts` used to be — `CrudService::new(pool, metadata, permissions)` takes its dependencies directly, and a downstream binary's own `main.rs` (e.g. `../metap-demo-crm/src/main.rs`, or `templates/metap-app`'s scaffold) does the wiring inline (connect DB, register entities, build `PermissionService`, build `AppState`, build the router, serve). Routes receive `AppState` (an axum `State` extractor) and call into `CrudService`; they never touch `sqlx`/`lapin` directly.

`metap_http::build_router(state, cors_origins)` takes the registered entities indirectly via `AppState`'s `MetadataRegistry` — it does not know about `crm.customers` or any other business entity. A second business module would be a new binary crate registering its own entities, not a hardcoded entity import into any `metap-*` library crate.

### Metadata-driven records

By default, business records live in one generic `records` table (`crates/migrations/*.sql`, originally generated from `packages/core/src/infra/db/schema.ts` before that was removed): tenant/entity/status/code columns plus a `data jsonb` column for the metadata-driven fields, with a `version` column for optimistic locking (fully implemented, not just reserved — `CrudService::update`/`delete` both gate their write on `WHERE version = $n`, returning `409 version_conflict` on a mismatch). Entities are defined as `EntityDefinition` values (`crates/metap-metadata/src/entity.rs`) — see `../metap-demo-crm/src/entities/customer_entity.rs` (or `templates/metap-app/src/example_entity.rs` for a from-scratch starting point) for the pattern: field/list-view/workflow metadata, no separate validation-schema object (see `metap-crud/src/validation.rs`'s doc comment for why) — and registered into `MetadataRegistry` by whichever binary owns them (see that same `main.rs`), not inside any `metap-*` library crate. Adding a new business entity means adding a new entity-definition module and registering it in the owning binary's `main.rs`, not creating a new table or route by hand.

**Table-per-entity is real now (Phase 21, `../metap-demo-jira`), not just `metap-reconciler`'s library surface.** `EntityDefinition.table_name` (set to `"records"` by every `../metap-demo-crm` entity, unchanged) is genuinely consulted end to end: `CrudService`/`QueryPlanner` route every query by it, and a `table_name` produced by `metap_reconciler::qualified_table_name_for("some.entity")` (a dedicated per-entity table, always schema-qualified into `ENTITY_SCHEMA` — `"entities"`, never `public` — reconciled at boot via `reconcile()`) works as a full drop-in alternative — `list`/`create`/`update`/`transition`/`delete`, Reference-field FK/list-view hydration, and the pre-delete reference-integrity guard (`find_referencing_record`, now grouped per physical table) all handle both. A dedicated table always lives in `entities`, never alongside the platform's own `public`-schema framework tables (`users`/`policies`/`records`/...) — real feedback: an earlier version put them in the same schema, making the boundary invisible from a plain `\dt`. A `Reference` field's target must also be on a dedicated table if it's referenced from one (`compile()` always builds the FK against `qualified_table_name_for(ref_entity)`, whether or not that entity is actually reconciled — see `../metap-demo-jira`'s `project_entity.rs` for why both of its entities are dedicated, not just one). Still no per-tenant fan-out — see `metap-reconciler`'s bullet above.

The roadmap (`docs/roadmap.md`, Data Model Strategy in `docs/architectures/05-building-blocks.md`) explicitly plans to peel off dedicated typed tables for high-volume or accounting-critical modules later — the generic JSONB table is a deliberate starting point, not an oversight.

### Core services and their fixed boundaries

- **`MetadataRegistry`** (`metap-metadata`) — owns entity definitions (fields, list views, workflow). Read-only after boot, populated once by whichever binary registers entities.
- **`CrudService`** (`metap-crud`) — the only thing routes call for record operations. Orchestrates: permission check -> field-metadata-driven validation -> query planning -> DB write -> workflow status assignment -> outbox enqueue.
- **`PermissionService`** (`metap-permission`) — tenant scope, RBAC/ABAC, field- and record-level permission. Real implementation (not a scaffold) — policies are stored via the `PolicyStore` trait (`PostgresPolicyStore` is the only impl today). **Entity-level permission is deny-by-default** (no matching policy → forbidden); **field- and record-level permission are allow-by-default** when no policy exists at all for that field/action (a newly added field is world-readable/writable to anyone who can already read/update the entity, until a field policy says otherwise) — see `PermissionSnapshot::filter_readable_fields`/`writable_fields`/`can_perform_record_condition`'s own doc comments for the exact rules per case.
- **`QueryPlanner`** (`metap-query`, `plan_list`) — the *only* place list/filter/sort queries are turned into SQL. Every list has a max limit, every query is tenant-scoped, filter/sort fields must come from entity metadata (never arbitrary client-supplied operators).
- **Workflow functions** (`metap-workflow`) — metadata-driven state machine (state field, initial state, terminal states, transitions). Fully implemented: initial-status resolution, transition lookup, guard evaluation (a `PolicyCondition`, not a function), the audit log, and outbox emits on transition/create/update/delete.
- **`EventBus`** (`metap-infra`) — a trait (`RabbitEventBus` is the only impl) events are published through; `metap-infra::outbox::enqueue` writes to the `outbox_events` table in the same transaction as the business write (outbox pattern), so RabbitMQ downtime can't lose events. `outbox-publisher` is the separate long-running process that drains and publishes them by default — a distinct binary from any downstream host process, not a background task inside them (unless a host process opts into running it inline instead: `NOTIFICATION_WORKER_INLINE=true` for `notification-worker` on `../metap-demo-crm`, `OUTBOX_WORKER_INLINE=true` for `outbox-publisher` itself on `../metap-demo-jira` — see both crates' bullets above). `EventBus::subscribe` is the read side, added once `notification-worker` needed a real consumer.

### Boundaries to preserve

From `docs/architectures/05-building-blocks.md`, still true of the current code and worth enforcing in review:

- Route/handler code must not import `sqlx`/`lapin` directly — go through `CrudService`/`metap-infra`'s `EventBus`.
- Frontend/client query input must not map directly to SQL operators — it goes through `QueryPlanner`, constrained by entity metadata.
- Workflow side effects are emitted through the outbox, never published to RabbitMQ directly from a service.
- Every business route assumes tenant scope and real auth (JWT + a live `user_roles` lookup per request — no defaulting, no caching roles on the token).
- No `metap-*` library crate gets business-entity knowledge — that's a downstream binary's job (`../metap-demo-crm`, `../metap-demo-jira`, or a new one).

## Frontend

This repo has no frontend of its own — `@metap/platform-ui` (`../platform-ui`) and `@metap/ui`
(`../design-system`) are both separate sibling repos with their own READMEs/CLAUDE.md, and the
only apps that actually run them (`@metap/crm-fe`, `@metap/jira-fe`) now live inside
`../metap-demo-crm/web`/`../metap-demo-jira/web` — see "No example apps in this repo" above.
Working on `platform-ui`/`design-system` themselves means going into those repos directly; running
a consumer to see changes reflected means going into one of the sibling demo repos and following
its own `web/README.md`.

Real local-login exists (`docs/roadmap.md` Phase 15, 2026-08-09 on): `POST /auth/login`
(email+password, argon2id-hashed against the `users` table) mints a JWT, which the frontend's
`/login` screen (`LoginForm` in `@metap/platform-ui`) uses — the same screen `RequireAuth`
redirects to when there's no token. Provision a user with `dev-tools create-user <tenantId>
<email> <password>` (dev-seeding, `cargo run --manifest-path crates/dev-tools/Cargo.toml --
create-user ...` from a downstream repo) or `POST /admin/users` (admin-driven, optionally
assigning roles in the same call); `dev-tools mint-token`/`seed-admin` still work unchanged for
minting a token by hand without going through a real login.

**Session survives reload since 2026-09-03** (`docs/roadmap.md` Phase 64, reversing the previous
"lives only in memory, lost on refresh — deliberate" note that used to be here): `POST /auth/login`
and the OIDC callback now set the JWT as an `HttpOnly` cookie (`crates/metap-http/src/cookies.rs`)
instead of only returning it in the JSON body, and `crates/metap-http/src/auth.rs`'s `AuthContext`
extractor accepts that cookie as a fallback whenever no `Authorization` header is present — Bearer/
Basic/`dev-tools mint-token` output are all completely unaffected, this is additive. A second,
non-`HttpOnly` cookie plus a required `X-CSRF-Token` header on any cookie-authenticated mutating
request is the double-submit CSRF defense a cookie-based session needs that a bearer header never
did. `@metap/platform-ui` no longer holds a token in React state at all — `AuthContext`'s `status`
(`"unknown"|"authenticated"|"anonymous"`) is derived from a `GET /auth/me` bootstrap check instead,
and every `apiFetch` call sends `credentials: "include"` plus the CSRF header automatically.
`crates/graphql-gateway` is the one exception (`Authorization: Bearer` only, decode-only, its own
keypair — see that crate's `authenticate` function) — the frontend calls the new `GET /auth/token`
route to mint a fresh short-lived Bearer token on demand right before each gateway call, rather
than holding one long-lived, so the thing this migration was for isn't reintroduced through that
one path.

### Metadata types stay generated, not hand-written

`../platform-ui/src/metadata/types.ts` (`EntityField`/`EntityWorkflow`/`EntitySummary`/etc.) is a thin façade over `../platform-ui/src/metadata/generated-types.ts`, which is generated — never hand-edit `generated-types.ts` directly. After a backend meta-model change (a new `EntityField` property, etc.), start any backend that has the change (e.g. `cd ../metap-demo-crm && cargo run`), then `cd ../platform-ui && pnpm generate:types` — run from inside that sibling repo, not from here — and commit the regenerated file there. The source of truth for what's in the generated types is `crates/metap-metadata/src/openapi.rs`'s hand-written `EntitySummary` JSON Schema (there's no Zod-equivalent reflection step in Rust, so this is maintained by hand rather than derived — see that file's doc comment; it must stay in sync with `entity.rs`'s structs). `GET /metadata/openapi.json` is intentionally public (no auth) so this codegen step can run without a minted token — it only describes API shape (entity/field names and kinds), never tenant data.
