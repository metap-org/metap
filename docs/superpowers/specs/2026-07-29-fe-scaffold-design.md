# Frontend Slice #1: Scaffold + Dev-Login + API/Metadata Client

Date: 2026-07-29

Status: approved

Scope: first slice of roadmap Phase 6 (Frontend Core). Phase 6's full goal list (app shell, `api-client`, `metadata-client`, `GeneratedList`, `GeneratedForm`, `WorkflowActionBar`, permission-aware UI, virtualization) is too large for one pass — this spec covers only enough to prove the whole pipeline works end to end: a booting app, a way to authenticate against the existing verify-only backend, a typed API client, a metadata client, and one hardcoded (not yet metadata-driven) list page. `GeneratedList`, `GeneratedForm`, and `WorkflowActionBar` are separate, later slices.

## Motivation

There is no frontend code in this repo at all yet. Before building the metadata-driven generated components Phase 6 ultimately wants, there needs to be a working app shell that can actually reach the backend — including solving a gap the backend's own design deliberately left open: metap's auth is "verify-only" (it never issues tokens), so there is currently no way for a browser to obtain one.

## Design

### Where this code lives, and platform vs. demo separation

metap is a platform meant to be imported by separate downstream projects that implement actual business apps — not the place those apps get built. Concretely for this slice: `web/` (one Vite package, not yet a nested workspace) keeps two things clearly separated by folder, even though they ship in the same package for now:

- `web/src/platform/` — the reusable pieces this spec builds (`api-client`, `metadata-client`, the auth context) that a future downstream project would import. Later slices' `GeneratedList`/`GeneratedForm` also land here.
- `web/src/demo/` — `DevLoginPage` and `CustomersPage`. These are a development/testing harness for the platform code, not a real business app — the same role a component library's own demo/playground app plays in its own repo, distinct from what a real consumer would build.

This folder split anticipates a future real package split (e.g. `web/` becoming its own publishable package, with the demo app moved to a separate consuming project) without doing that work now — same reasoning as the backend's own target-architecture doc (`docs/architectures/index.md`'s "Target Architecture: Multi-Service Evolution"): don't build the package/workspace split until a second, real consumer actually needs to import `web/src/platform` from outside this repo. Until then, one `package.json` for the whole `web/` directory is enough.

Developers run it independently: `cd web && pnpm install && pnpm dev`.

### Stack

- **Vite** + **React** + **TypeScript** — Vite's default dev port is 5173, which `.env.example`'s `CORS_ORIGINS` already includes, confirming this was the anticipated choice.
- **Mantine** for UI components (tables, forms, notifications) — chosen for its breadth (needed later for `GeneratedForm`'s field renderers) without MUI's weight.
- **TanStack Query** for server state — per roadmap.
- **React Router** for routing (the `/dev-login` screen plus the main app).
- Vite dev server proxies `/api`, `/metadata`, `/health` to `http://localhost:3000` (the existing backend dev server), so the frontend never needs a hardcoded backend origin and there's no CORS friction locally.

### Auth: a temporary dev-login screen, no backend changes

metap's backend stays exactly as designed (verify-only, no `/login`, no token issuance) — this spec does not touch it except adding one small dev-convenience script (see below). The frontend gets a `/dev-login` route: a textarea where a developer pastes a JWT they minted separately, and a button that stores it and redirects into the app.

**Token storage: in-memory only (a React context), never `localStorage` or `sessionStorage`.** This is a direct, deliberate departure from the legacy system's pattern (audited earlier in this project): storing the entire session — token, user id, role/function permissions, even a signature image — in `localStorage`, where any XSS on the page becomes a full session takeover. An in-memory token is lost on page refresh, which is an acceptable, honest cost for a screen that's explicitly temporary scaffolding, not a real login system.

**Getting a token to paste:** promote the ad-hoc `node -e` snippet used throughout backend development into a real script, `scripts/mint-dev-token.mjs` in the **backend** repo (alongside the existing `scripts/generate-dev-jwt-keypair.mjs`), exposed as `pnpm mint-token [tenantId] [userId] [roles]`. It signs a token with `keys/dev-jwt-private.pem` (already generated by prior work) and prints it to stdout for copy-paste. This is a dev tool, not a new backend capability — it doesn't add a route, doesn't run inside the server process, and doesn't change what the backend accepts or verifies.

### `api-client` (`web/src/platform/api/client.ts`)

A small wrapper around `fetch`, using relative URLs (`/api/...`, `/metadata/...`) so the Vite proxy handles routing in dev and the same code works if the frontend is ever served from the same origin later. Attaches `Authorization: Bearer <token>` from the auth context (`web/src/platform/auth/AuthContext.tsx`). On a non-2xx response, parses the backend's structured error shape (`{ error: { code, message, requestId, traceId } }`, already established by the auth-kernel work) and throws a typed `ApiError` carrying `status`/`code`/`message` — callers (React Query hooks) get a real, typed error, not a generic fetch failure.

### `metadata-client` (`web/src/platform/metadata/useEntities.ts`)

One TanStack Query hook, `useEntities()`, wrapping `GET /metadata/entities`, typed against the shape `MetadataRegistry.listEntities()` already returns (`name`, `label`, `fields`, `listViews`, `workflow`). Used for a simple landing page listing the registered entities — not yet driving any generated rendering (that's the next slice).

### Proof-of-life list page (`web/src/demo/CustomersPage.tsx`)

One hardcoded (not metadata-driven) page that calls `GET /api/crm.customers?limit=30` through the api-client and renders the results in a plain Mantine `Table` (id, code, name, status columns). This exists purely to prove the whole chain — dev-login → api-client → real backend → real Postgres data — actually works end to end before investing in the generated, metadata-driven version. It lives in `web/src/demo/`, not `web/src/platform/`, because it's a harness for exercising the platform code, not part of the platform itself.

## Out of scope (this slice)

- `GeneratedList` / `GeneratedForm` (metadata-driven rendering, field-kind-aware inputs, table virtualization) — next slice(s).
- `WorkflowActionBar` — deferred until the backend has real workflow transitions (roadmap Phase 5, not yet built).
- Permission-aware UI state beyond what's naturally visible (the frontend doesn't need to hide anything yet; there's one entity and no restrictive `permissions` block declared on it).
- Any backend changes beyond the one dev-only minting script.
- Real login/session management (password auth, refresh tokens, httpOnly cookies) — this is explicitly a temporary developer convenience, not a step toward production auth. Real auth issuance is its own future project.

## Testing (minimal — this slice is scaffolding, not business logic)

No automated tests for this slice. It's wiring (build tooling, routing, a dev-only auth shim, a thin fetch wrapper, one hardcoded page) rather than logic with edge cases worth locking in — the manual end-to-end verification (mint a token, paste it, see the entity list, see the customer list) exercises the real path, including the real error-shape parsing on a bad/expired token. Automated FE tests can start once there's actual logic to protect (e.g. `GeneratedForm`'s field-kind-to-input mapping in the next slice).
