# FE Verification Findings — 2026-08-02

Findings from the Playwright-driven verification pass described in
`docs/superpowers/specs/2026-08-02-fe-manual-verification-design.md` and
`docs/superpowers/plans/2026-08-02-fe-manual-verification-plan.md`. Entries
are in the order found, not pre-sorted by severity or priority — priority is
set by review of this list, not by this document.

Two sessions were driven end-to-end against the real running app
(`packages/platform-react` + `apps/demo`, backed by the real `apps/crm` API
and Postgres): an admin-role session covering dev-login, entity browsing,
sort/filter/search, infinite-scroll pagination + row virtualization, create,
the reference-field picker, record detail, edit, a guarded workflow
transition, delete, and two error states; and a restricted-role ("viewer")
session covering field-level read/write permission masking and an
unauthorized delete attempt.

### 1. Validation errors show raw Zod messages, not user-facing text

- **Flow:** 11 (error states)
- **Severity:** minor
- **Repro:** Go to `/records/crm.customers/new`, click **Save** without
  filling in any fields.
- **Expected vs actual:** Expected a plain-language message like "Code is
  required." Actual: the **Code** and **Name** fields both show "Invalid
  input: expected string, received undefined" — the raw Zod validation
  message, passed through unmodified from the backend's `fieldErrors`
  response.
- **Likely location:** `packages/platform-react/src/form/GeneratedForm.tsx:104`
  (`setFieldErrors(error.fieldErrors ?? {})` — no message translation layer)
  and/or the backend's Zod error serialization in the create/update route.

### 2. Non-401 API errors render as unstyled, dead-end plain text

- **Flow:** 11 (error states)
- **Severity:** minor
- **Repro:** Navigate to `/records/crm.customers/00000000-0000-0000-0000-000000000000`
  (a valid UUID that doesn't exist).
- **Expected vs actual:** Expected a styled error state consistent with the
  rest of the app (Mantine `Alert`, as used elsewhere for delete/workflow
  errors), ideally with a way back to the list. Actual: an unstyled
  `<div>Error: Record not found.</div>` at the top-left of an otherwise blank
  page — no layout, no navigation, a genuine dead end (only the browser Back
  button recovers).
- **Likely location:** `packages/platform-react/src/api/ApiErrorMessage.tsx:15`
  — only the 401 case (`error.status === 401`) gets a real recovery action
  ("Sign in again" link); every other status falls through to bare text.

### 3. `ReferenceFieldValue` shows the raw internal UUID while its own fetch is still loading

- **Flow:** 5 / 10 (RecordDetail, both admin and viewer sessions)
- **Severity:** minor
- **Repro:** Open a record detail page for a record with a reference field
  set (e.g. `crm.customers` record B, `referredBy` pointing at record A),
  and capture the page immediately after the main record/entity queries
  resolve but before the nested reference lookup finishes. Observed directly
  in the viewer-role run: a screenshot taken right after navigation still
  showed the whole page's "Loading..." state, but a body-text read taken a
  moment later (main content now rendered) showed **Referred By:
  `ae574916-1690-4699-986f-ca01b015d5ba`** instead of "Verify Customer A" —
  confirmed via a direct `GET /api/crm.customers/<id>` call with the same
  viewer token that the backend correctly returns `data.name: "Verify
  Customer A"`, so this is a frontend timing/fallback issue, not a
  permission bug.
- **Expected vs actual:** Expected either a loading placeholder (e.g. "…")
  or for the value to simply not render until resolved. Actual: the raw,
  meaningless-to-users UUID is shown as if it were the final value, because
  the component falls back to the raw id whenever its own record fetch
  hasn't resolved yet (same fallback path as an actual fetch failure — the
  two cases aren't distinguished).
- **Likely location:** `packages/platform-react/src/field/ReferenceFieldValue.tsx:27-28`
  — `const raw = record && field.refDisplayField ? record.data[...] : undefined;`
  then `return <>{typeof raw === "string" ? raw : id}</>;` unconditionally
  falls back to `id`, whether the query is still loading or genuinely failed.

### 4. No client-side way back to the list from RecordDetail or GeneratedForm

- **Flow:** 5, 6 (RecordDetail, GeneratedForm/edit)
- **Severity:** minor
- **Repro:** Open any record's detail or edit page.
- **Expected vs actual:** Expected some way back to the entity's list without
  the browser Back button (a breadcrumb, a "Back to list" link, or similar).
  Actual: `RecordDetail` only renders **Edit** and **Delete**;
  `GeneratedForm` only renders **Save** — neither links back to
  `/records/:entityName`. This is a direct instance of the missing
  layout-shell/navigation-chrome gap already flagged as its own upcoming
  FE-foundation sub-project, surfaced concretely here.
- **Likely location:** `packages/platform-react/src/detail/RecordDetail.tsx`,
  `packages/platform-react/src/form/GeneratedForm.tsx`.

### 5. Delete cannot be restricted by policy — a "viewer" role deleted a record it should arguably not be able to

- **Flow:** 10 (permission-aware UI, viewer session)
- **Severity:** major
- **Repro:** As a non-admin role with no entity-level policies at all (the
  default-allow state — see `PermissionService.checkAction`, which allows
  everything when zero policies match), open a record's list and click
  **Delete**.
- **Expected vs actual:** Confirmed empirically: the viewer session's delete
  attempt on record `VERIFY-B` succeeded (`deleted: true` in the DB
  afterward) — identical to what an admin could do. This was already
  predictable ahead of the run (noted during Task 2 setup) because
  `CreatePolicyBodySchema` (`packages/core/src/server/routes/admin.ts`) only
  accepts `action: "read" | "create" | "update" | "write"` — there is no way
  to create a `"delete"`-action policy through the admin API at all, even
  though `PermissionService.canDeleteEntity` checks the store for exactly
  that action. Every other action (read/create/update, both entity- and
  field-level) can be restricted; delete cannot be restricted by policy at
  all today.
- **Likely location:** `packages/core/src/server/routes/admin.ts` (`CreatePolicyBodySchema`'s
  `action` enum), `packages/core/src/core/permission/permission-service.ts`
  (`canDeleteEntity`/`EntityAction`).
