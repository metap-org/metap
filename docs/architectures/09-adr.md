## Notable decisions not covered by a dedicated spec

- **`core->modules` layering**: `packages/core` must never import a specific business entity — entity registration is an application-layer concern owned by each `apps/<module>` (e.g. `apps/crm/src/modules/registry.ts`, called after `createContainer()`/`buildApp()` return). Originally fixed as a convention during the Metadata Compiler work; now also a hard package boundary (`packages/core` has no dependency path to any `apps/*` package) since the 2026-08-02 monorepo restructure.
- **Index expression must match the query expression exactly**: an `IndexReconciler`-built index on `data->>'field'` is *never* selected by Postgres for a query written as `jsonb_extract_path_text(data, 'field')`, even though they're semantically equal — Postgres's expression-index matching is syntactic, not semantic. Every index this codebase builds uses `jsonb_extract_path_text`, matching `QueryPlanner`'s own filter/sort expression. Found and fixed during the Hot Field Index Strategy work.
- **Postgres DDL accepts no bind parameters at all** (not just under `CONCURRENTLY`) — `IndexReconciler` inlines entity/field names as escaped SQL literals, safe only because they come exclusively from server-authored, `MetadataCompiler`-validated metadata, never request input.
- **`PermissionService.scopedTenant` fails loudly instead of defaulting a missing tenant**: it used to fall back to a hardcoded tenant UUID when `context.tenantId` was empty (and took `Partial<RequestContext>`, weaker than necessary — every real call site already had a full `RequestContext`). Flagged by an external architecture review (2026-08-02); fixed by tightening the parameter type to `RequestContext` and throwing if `tenantId` is empty, since that can only mean a bug upstream — see [08. Cross-cutting Concepts](08-cross-cutting.md#multi-tenancy).
- **FE Playwright/E2E verification effort scoped, then abandoned (2026-08-07)**: the manual-verification and committed-E2E-test-suite direction (specs/plans/findings dated 2026-08-02–2026-08-03) was designed and partially planned, then explicitly cancelled before any Playwright code was written — no test infrastructure was ever added to the repo. The specs/plans/findings docs were deleted rather than left to rot. If committed E2E coverage is wanted again later, treat it as a fresh decision, not a resumption of this one.
- **Architecture review conducted; `EventBus` interface identified as the one near-term action (2026-08-07)**: `docs/architecture-review-2026-08-07.md` reviewed every core component against its actual trigger (not hypothetically) and found the codebase has exactly one existing infra-seam precedent, `PolicyStore` (`packages/core/src/core/permission/policy-store.ts`). Recommended extending that same pattern to event publishing — promote `RabbitPublisher`'s type to an `EventBus` interface, change `OutboxService`'s constructor to depend on it — as the only currently-triggered abstraction; **not yet implemented**. Also surfaced, to be fixed separately: `CLAUDE.md`'s description of `WorkflowEngine` ("transition/guard logic is not yet implemented") is stale relative to `docs/roadmap.md` Phase 5's actual, done, tested state.
- **Modular-first Capability SPI target named, not adopted (2026-08-07)**: `docs/modular-spi-architecture.md` records a proposed target shape — Level 1 Programming Model / Level 2 Capability SPI (`Storage`/`EventBus`/`Scheduler`/`Identity`/`Cache`/`Search`/`WorkflowRuntime`) / Level 3 Providers — plus deployment profiles (Tiny/Business/Enterprise/Cloud) and a `deployment: remote` per-module config switch, aimed at letting the same source run as a single binary or a distributed system. Explicitly **not** a build commitment for the six SPIs beyond `EventBus`, and **not** a change to `docs/architectures/02-constraints.md`'s current Postgres/RabbitMQ-only binding — recorded as a named destination so near-term decisions aim consistently, without pulling the rest forward ahead of their triggers.
- **`packages/core` moves to Rust — decided, Option B (2026-08-07)**: full write-up in `docs/rust-core-viability.md`. Rejected as a full-core rewrite on a first pass (no measured performance trigger), reopened on a sharper case (minimal-footprint deployment, plus contributor draw), grounded with a spike (Rust rewrite of the outbox-publisher worker, `experiments/rust-outbox-poc/`, benchmarked against a matching Node implementation): Rust won on all 4 measured metrics — binary size (3.1 MB vs. Node's 118 MB runtime), cold start (~4–5x faster), idle RSS (~5x lower), and throughput (~6–8% higher across 5 runs each, once an early spike bug — awaiting an unused RabbitMQ publisher-confirm — was fixed). Decision: **Option B, Rust for all of `packages/core`, every deployment profile**, not scoped to a single Tiny-profile binary. Frontend type codegen is unaffected — `packages/platform-react`'s `generate:types` already consumes `/metadata/openapi.json` over HTTP, not TypeScript/Zod source directly, so a Rust-served equivalent document requires no frontend change. Zod's runtime-validation role is replaced by a validator generated from `EntityField[]` metadata directly (no per-entity hand-authored schema), which also matches what Phase 11's DB-authored metadata will need anyway. Contributor-pool-split risk is addressed by keeping entity/workflow/permission *authoring* declarative and data-shaped, concentrating Rust expertise in a smaller core-engine team.
- **Rust port completed, TS stack deleted, repo restructured (2026-08-07 to 2026-08-08)**: `crates/metap-*` (9-crate Cargo workspace) + `apps/crm-server` fully replace `packages/core`/`apps/crm`, which were deleted after verifying the new stack end-to-end against a database migrated from scratch by `db-migrate` alone — see `docs/rust-core-viability.md`'s Migration Order and "TS Removal" section for the full account, including the two real bugs (a `data`/`status`-defaulting gap, a CORS-config panic) and one test-isolation bug (unscoped `outbox_events` cleanup in a parallel test run) caught only by live/e2e verification, all fixed. The Cargo workspace root was later hoisted from a nested `Cargo.toml` to the repo root and `rust/` renamed to `crates/`, matching pnpm's existing root-level ergonomics. `EventBus` (Part 2's near-term recommendation from `docs/architecture-review-2026-08-07.md`, superseded as a standalone TS refactor by the full Rust rewrite) exists in the Rust port from the start as a `metap-infra::EventBus` trait, not added later as a separate step. **Known gap surfaced at the time, closed 2026-08-08** (see the next entry): admin HTTP routes (policy CRUD, role grant/revoke) didn't exist over HTTP yet.
- **`docs/architectures/*.md` refreshed to describe the Rust implementation directly; admin HTTP routes added (2026-08-08)**: sections 01-08 (previously accurate for the deleted TS stack: Fastify/Zod/Drizzle, `packages/core`/`apps/crm`, a `container.ts`-style DI container) rewritten to name the actual Rust crates/types/file paths (axum, sqlx, `metap-crud::CrudService`, `apps/crm-server/src/main.rs`'s inline wiring, etc.), closing a documentation-drift gap of the same kind `docs/architecture-review-2026-08-07.md` flagged for `CLAUDE.md` (now also fixed). `docs/why.md`/`docs/low-code-*.md` were deliberately left as-is (each already either explains the *unchanged* pre-Rust reasoning, or already carries its own "predates the Rust decision, retarget when implemented" note, matching Phase 11's roadmap item to retarget those specifically when they're actually implemented, not preemptively); `docs/vision.md`/`docs/modular-spi-architecture.md` got small stale-path fixes only, not a rewrite. Same pass added the admin HTTP surface that closed the gap named above: `crates/metap-http/src/routes/admin.rs` (`/admin/users`, `/admin/users/{userId}/roles[/{role}]`, `/admin/policies[/{id}]`, `/admin/policies/explain`), gated by a new `AdminContext` extractor (`auth.rs`) requiring the `admin` role, wired into `AppState` (which now also holds `permissions: Arc<PermissionService>` directly, not just inside `CrudService`) — verified live against a real Postgres/RabbitMQ dev stack, not just `cargo test`.
