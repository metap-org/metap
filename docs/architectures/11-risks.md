# 11. Risks and Technical Debt

Honest, grounded list — not padded with hypotheticals. Each item names its actual trigger for being addressed, per this project's trigger-based evolution stance ([04. Solution Strategy](04-strategy.md)).

| Risk / Debt | Impact | Trigger to address |
|---|---|---|
| Single generic `records` table for every entity | A very high-volume or accounting-critical entity shares indexes/row layout with everything else; JSONB access is slower than a typed column for heavy write/aggregate workloads | A concrete entity's measured performance need — see Data Model Strategy Step 3, [05. Building Block View](05-building-blocks.md) |
| No report/analytics query path | A future dashboard or export feature would have to run directly against the OLTP `records` table, competing with live traffic | A real reporting UI/consumer shows up, or an OLTP-path query is measurably slowed by report-shaped access — see `docs/roadmap.md` Phase 4 |
| Phase 8 (Hardening) not started | No documented production security/ops posture: no confirmed non-root container setup, no secrets-management audit, no tuned rate limits beyond the default 300/min | Approaching a real production deployment |
| No production deployment topology documented | No load balancer, no orchestrator config, no autoscaling, no secrets manager — see [07. Deployment View](07-deployment.md) | Same as Hardening trigger above |
| Single PostgreSQL instance, single RabbitMQ instance | No HA/replica story; a DB outage stops both reads and writes on the API (the outbox worker degrades gracefully by design, the API does not) | Real uptime requirements being defined (part of Hardening) |
| `IndexReconciler` has no build-concurrency governor | A metadata change adding several new `indexed`/`unique`/`searchMode` fields at once could trigger several concurrent `CREATE INDEX CONCURRENTLY` builds against the same DB at boot | Observed contention in practice — no entity has needed more than 2-3 indexed fields so far |
| `apps/crm` not actually deployed as a separate process | `packages/core`/`apps/crm` are separate *packages* now (2026-08-02), but there's still only one module and no deployment infra (Docker images, process manager, orchestrator) to actually run `apps/<module>` as independently-deployed units | A second real business module gets built, or real deployment infra gets set up — see [04. Solution Strategy](04-strategy.md)'s "Multi-Service Split" |
| `packages/platform-react` not published to a registry | It's a real workspace package now (2026-08-02), consumed by `apps/demo` via `workspace:*`, but still `private: true` — an external (non-workspace) downstream project would have to vendor the code, not `npm install` it | An actual external consumer (outside this workspace) needs to import it — see [04. Solution Strategy](04-strategy.md)'s "Frontend Platform Package" |
| Outbox worker holds its DB transaction open for the whole publish-to-RabbitMQ call | Deliberate tradeoff (see `docs/superpowers/specs/2026-08-02-outbox-row-locking-design.md`) — simple, correct, standard for a modest-throughput job queue, but holds a row lock for the duration of a network call. An external architecture review (2026-08-02) suggested the alternative shape instead: claim rows in a short transaction, commit, publish outside it, ack in a follow-up write, with a lease/reclaim mechanism for abandoned rows | Measured lock contention or publish latency once real throughput or RabbitMQ latency is understood — not a problem yet at today's scale |
| Boot-time maintenance work (`MetadataDriftService.check`, `IndexReconciler.reconcile`) runs inline in `buildApp()` | Couples the API's request-serving startup path to operational/DB-maintenance work — a slow index build or drift check delays the server accepting its first request | Approaching production hardening (same category as Phase 8) — move to an explicit command/worker, keep a config flag for local dev convenience |

## Already-mitigated risks (kept for institutional memory)

- **Record-level read policy could empty an admin's `list()` results.** Found during Phase 3 manual E2E verification, fixed 2026-08-01 with a regression test — see [09. Architecture Decisions](09-adr.md).
- **Field masking didn't cover top-level `code`/`status` mirror columns.** Same fix pass as above.
- **An `IndexReconciler`-built index was silently never used** because its expression (`data->>'field'`) didn't syntactically match `QueryPlanner`'s query expression (`jsonb_extract_path_text`). Found and fixed during the Hot Field Index Strategy sub-project, before it was ever committed — see [09. Architecture Decisions](09-adr.md).
- **Frontend Core (Phase 6) is now fully done** — `GeneratedForm`, `WorkflowActionBar`, permission-aware UI state, and paginated/virtualized `GeneratedList` all shipped 2026-08-02, closing what was previously listed here as "Frontend Core only Partial".
- **`OutboxService.publishPending()` could double-publish the same event.** No row locking meant two concurrent outbox workers (which the monorepo restructure makes possible — one per `apps/<module>`) would select and publish the same pending rows. Found while reviewing DB-coupling risks, fixed 2026-08-02 with `SELECT ... FOR UPDATE SKIP LOCKED` — see [09. Architecture Decisions](09-adr.md).
- **`packages/platform-react`'s metadata types were a hand-maintained, already-drifted mirror** of backend's entity shape (missing `indexed`/`unique`/`searchMode` by the time it was caught). Fixed 2026-08-02 by generating them from backend's OpenAPI doc instead — see [09. Architecture Decisions](09-adr.md).
- **`PermissionService.scopedTenant` silently defaulted to a hardcoded tenant UUID** when `context.tenantId` was empty, which could have masked an upstream bug as wrong-but-quiet cross-tenant-looking results. Flagged by an external architecture review, fixed 2026-08-02 to throw instead — see [08. Cross-cutting Concepts](08-cross-cutting.md#multi-tenancy).
- **`packages/platform-react` hard-depended on `react-router-dom`.** `ApiErrorMessage`/`GeneratedList`/`RecordDetail` called `Link`/`useNavigate` directly, so a consumer using a different router (or none) couldn't use them as-is. Fixed 2026-08-02 with an injected `NavigationAdapter` (React Context) covering the 5 navigation actions these components need; `apps/demo` provides the only implementation today, backed by `react-router-dom` — see `docs/superpowers/specs/2026-08-02-platform-react-navigation-decoupling-design.md`.
